# Changelog

## [3.0.2] - 2026-08-15

### Fixes
- **Fixed: the image-gen guidance block was too weak to override the upstream SKILL.md around it.** The managed block was appended to a file whose own body teaches `OPENAI_API_KEY`, a `.env` file, `OPENAI_BASE_URL`, `--api-key` / `--base-url` flags, `--mask` inpainting, bare `gpt-image-*` model ids, and `python scripts/image_gen.py` for every example. Two coherent but contradictory sets of instructions sat in one file, and the block only said "prefer ours" — it never said the upstream ones were dead. A model reading the file could reasonably pick the upstream path, and one did: it invoked `~/.claude/skills/image-gen/scripts/image_gen.py` directly, hit the missing `OPENAI_API_KEY`, and told the user to `export OPENAI_API_KEY=sk-...` or create a `.env` in the skill directory — none of which has anything to do with this wrapper. The block is rewritten as an explicit override: it opens by declaring that it supersedes everything above it, names `python3 ~/.claude/scripts/image-gen-openrouter.py` as the sole entry point, and then **enumerates each superseded upstream instruction by name** and marks it inoperative. It also documents what the wrapper actually accepts (including `--aspect-ratio`, `--resolution`, `--seed` and the `512`/`1K`/`2K`/`4K` size tiers, none of which upstream mentions), the real default model `openai/gpt-image-2`, and the meaning of exit codes `2` / `3` / `4` with the correct response to each — in every case, one that does not route back to `image_gen.py` or to an OpenAI variable. `install.ps1`'s `Get-ImageGenIntegrationBlock` carries the identical new text.
- **Fixed: the closing launcher table advertised commands the user never installed.** `cl_commands_hint` printed all five backend rows (`cl_claude` / `cl_glm` / `cl_or` / `cl_gpt` / `cl_ccr`) unconditionally, so a default install — which sets up `claude`, `glm` and `or` — still told the user about `cl_gpt` and `cl_ccr`. Those launchers are generated by `claude.zsh` from the installed profiles glob, so on that machine they do not exist and typing one gets `command not found`. Backend rows are now filtered against `$CLAUDE_DIR/profiles/*.json`; the generic rows (`cl` / `cl_auto`, `cl_switch`, `cl_profiles`, `cl_stop`) still always print.

### Design Rationale
- **Explicit negation, not just a stronger recommendation.** Telling a model "use the wrapper" leaves the upstream instructions standing as a plausible alternative, which is exactly how the failure happened: nothing in the file said `OPENAI_API_KEY` was wrong, only that another path existed. The block now lists `python scripts/image_gen.py`, `OPENAI_API_KEY`, `.env`, `OPENAI_BASE_URL`, `OPENAI_IMAGE_MODEL`, `--api-key`, `--base-url`, `--mask`, `--moderation` and the `gpt-image-*` model table one by one and says what each one is now. The scope of the override is bounded rather than total — the prompt-writing guidance and the `references/sample-prompts.md` recipe step are explicitly kept in force, so the block cannot be read as "ignore this whole file".
- **The block stays appended at the end of `SKILL.md` rather than being inserted after the frontmatter.** Moving it earlier would trade a small, speculative primacy gain for three concrete costs. Existing installs would not benefit anyway: the replace path rewrites the block *in place*, so every already-installed machine keeps it at the end unless a strip-and-reinsert migration is added, which would mean fresh and upgraded installs disagreeing on layout. Insertion would need frontmatter parsing (find line 1 `---`, find the closing `---`, handle a file with neither) duplicated across both installers, and `install.ps1` cannot be executed on the machine this was written on — the Bash side would be tested and the PowerShell side would be a blind port of *structural* logic, not just of a string. The block's byte-parity invariant, by contrast, is verified mechanically. Since the actual defect was the block's content and not its position, the content was fixed and the write path left untouched: `image_gen_augment_skill`, the strict marker validator, the legacy migration, and idempotency are all unchanged.
- **The filter reads the installed profiles, not `SELECTED_PROFILES`.** `SELECTED_PROFILES` records what *this run* chose, which is not the same as what the user can run: a re-install that deselects a backend leaves the previously installed profile in place (`install_profiles` only adds), and the launcher keys off the profile file, not off the run. The profiles directory is the same source `backend_setup_hints` already reads a few lines earlier, so the two hint blocks now agree by construction. Under `--dry-run` nothing has been written yet, so every row is shown.
- **Row-level filtering only; the model descriptions stay literal.** Deriving the `/model` column from each profile's `ANTHROPIC_DEFAULT_*_MODEL_NAME` would mean computing display widths for a hand-aligned CJK table, where a cell's column width is not its character count. The rows remain the exact pre-padded strings they were, printed or skipped, so alignment cannot regress. The table already points at `docs/BACKENDS.md` for the authoritative model list.

### Notes & Caveats
- **The block cannot repair a `SKILL.md` that has no block.** The machine that produced this report had a pure upstream `SKILL.md` — zero markers, no ownership manifest — because a previous incident overwrote the managed block. No amount of rewriting helps there; that state is fixed by re-running the installer, which now self-heals it via the 3.0.1 adoption path. This change makes the block harder to talk a model out of once it *is* present.
- **The frontmatter `description:` still says "OpenAI image generation API" with the `gpt-image-*` ids**, because it is upstream text and the augmentation deliberately preserves every byte outside the markers. It is what Claude Code matches on to route to the skill, so it is not load-bearing for how the skill then runs, and the block explicitly corrects the model ids. Rewriting frontmatter would put the installer in the business of editing upstream metadata, with a new class of parse failure on every upstream release.
- The two installers' blocks were re-verified byte-identical after the rewrite (79 lines each, `cmp` clean), and the 55-assertion fixture suite still passes under both bash 5.3 and the system bash 3.2: the write path did not move, so no test needed updating.
- `cl_stop [--all]` is still shown unconditionally, even though only profiles with a `service` block (`ccr`, `gpt`) can start anything. Conditioning it would need `jq` to read `.service`, and `cl_commands_hint` currently has no `jq` dependency — while running `cl_stop` with nothing running is harmless.
- `install.ps1` has no equivalent table and no profile installation: Windows has no `cl_*` runtime, and its "Next steps" block already says so. Nothing to sync.

## [3.0.1] - 2026-08-15

### Fixes
- **Fixed: the stale-manifest reconciliation deleted live ownership manifests.** `install_image_gen` removed the ownership manifest whenever `prior_owned` was false, and `prior_owned` is false for *two* different reasons — the skill directory being absent, or the marker check failing on a directory that is very much present. The comment and the warning text both said "no image-gen directory present", but the condition never tested for it. A user whose `SKILL.md` markers stopped matching (a hand edit, a truncated write, an interrupted upgrade) therefore had their perfectly valid manifest deleted on the next install, and the loss is unrecoverable: with the manifest gone the directory fails the ownership proof forever and every subsequent run skips it. The condition now requires `[[ ! -d "$skill_dir" ]]`, which is what the surrounding comment always claimed. `install.ps1` carried the identical bug and got the identical fix. Present since image-gen was introduced in `e1cfff6` (2026-08-02); unrelated to the 3.0.0 OpenRouter migration, which merely made the consequences visible.
- **Fixed: a directory that lost its manifest could never be recovered by the installer.** The "exists but is not installer-owned" branch returned before `image_gen_augment_skill` was ever reached, so once the manifest was gone the directory was permanently classified as user content and skipped. Ownership now has a second, independent proof: a byte-exact managed marker block (current or pre-OpenRouter layout) that passes the strict layout validator is itself evidence this installer wrote the file, since the markers are exact-line literals that only `image_gen_augment_skill` emits. Such a directory is now adopted — upgraded through the normal path, with a fresh manifest written on success. Affected machines self-heal on the next install instead of needing a manual `rm -rf ~/.claude/skills/image-gen`.
- **Fixed: the two bugs together produced a self-contradictory install.** `install_scripts` deletes every `SUPERSEDED_USER_SCRIPTS` entry unconditionally and knows nothing about the image-gen ownership decision made later in the run. When image-gen was skipped, the result was `~/.claude/scripts/image-gen-cliproxyapi.sh` deleted but `~/.claude/skills/image-gen/SKILL.md` still instructing Claude to call it — image generation failing on a dead path, with nothing in the output saying why. **This is the symptom affected users actually saw.** When the skip now happens, the installer checks whether the skipped `SKILL.md` still names a superseded wrapper and, if so, prints the exact breakage and both concrete repairs (reinstall, or the one-line hand edit) rather than only incrementing the warning counter.

### Design Rationale
- **Adoption widens the ownership test deliberately, and only by one axis.** The risk of a self-heal path is misclassifying a user's own directory as installer-owned and overwriting it. The marker block is a safe proof precisely because the strict validator is unforgiving: exactly one exact-line BEGIN, exactly one exact-line END, BEGIN before END, and no line carrying marker text without being an exact marker line. A user writing their own image-gen skill does not accidentally produce that. `_image_gen_dir_owned` itself was left strict (manifest **and** markers) rather than loosened, because uninstall also calls it and deletion should keep demanding the stronger proof; adoption is a separate predicate consulted only on the install path. A directory with neither proof is still skipped and never touched, and there is a regression test asserting exactly that.
- **The backup path had to learn that a manifest may be absent.** An adopted install is by definition one whose manifest is missing or unusable, so the mandatory pre-npx backup — which previously required copying both the directory and the manifest, and refused to proceed without both — would have rejected every adoption. Backup and restore now track a `backup_manifest` flag: the directory half is always required, the manifest half is backed up and validated only when a usable manifest existed. Rollback on a failed adoption therefore restores the prior `SKILL.md` byte-for-byte and fabricates no manifest, which is asserted by test V8f.

### Notes & Caveats
- Fixture coverage grew from 25 to 55 assertions. The three states the old suite could not see are now covered directly — `manifest=none + markers=legacy` (the exact real-machine state), `manifest=none + markers=current`, and `dir present + valid manifest + non-matching markers` (the self-destruct case, which now asserts the manifest **survives**) — plus an anti-overreach case asserting a directory with neither proof stays unowned. Run against the pre-fix installer, 13 of the new assertions fail; against the fix, all 55 pass.
- The new tests drive the real `install_image_gen` end to end against a stubbed `npx` and a throwaway `CLAUDE_DIR`, rather than testing the helper predicates in isolation. Testing the predicates is what let the original bug through: every helper was individually correct and the coordinator still never called the migration.
- `install.ps1` received the same four changes (absent-directory precondition, `Test-ImageGenDirAdoptable`, the superseded-wrapper warning, and the optional-manifest backup/restore). **They are unverified**: no PowerShell runtime was available on the machine where this was written, so the PowerShell edits are static ports reviewed by eye against the Bash originals and have not been executed.

### Features
- **New `or` backend — OpenRouter's Anthropic-compatible endpoint, direct.** `profiles/or.json` follows the `glm.json` shape exactly: `service` is `null`, no proxy is started, nothing is installed. `ANTHROPIC_BASE_URL` is `https://openrouter.ai/api` (no `/v1` — Claude Code appends `/v1/messages` itself), and the four model slots map to `deepseek/deepseek-v4-pro` (opus, sonnet) and `deepseek/deepseek-v4-flash` (haiku, fable). `cl_or` / `cl_or_auto` are generated by `claude.zsh` from the profiles glob, so the launcher needed no changes at all.
- **`gpt` and `ccr` are no longer ticked by default** in the installer's "Model Backends" group; `or` is. Only the `default_on` column of their `GROUP_ITEMS` entries changed — no code, template, or `configure_*` function was removed. Their descriptions now also name the dependency ("needs cliproxyapi", "manual web-UI setup") so it is visible at the point of choice.
- **`--all` installs every backend, now including `or`**: `SELECTED_PROFILES=("glm" "or" "gpt" "ccr")`.
- **`cl_commands_hint()` lists `cl_or`** alongside the other launchers in the post-install summary.

- **BREAKING: image generation moved off CLIProxyAPI onto OpenRouter.** The always-installed `sinedied/agent-skills:image-gen` Skill is now driven by `scripts/image-gen-openrouter.py`, a dependency-free Python wrapper that posts directly to `POST https://openrouter.ai/api/v1/images` with `openai/gpt-image-2`. The 538-line `scripts/image-gen-cliproxyapi.sh` is deleted, and with it the CLIProxyAPI binary requirement, the `v7.2.17` minimum, the loopback `:8317` endpoint, the `/healthz` liveness probe, the local client-key read, and the ChatGPT/Codex OAuth dependency. Image generation no longer requires any local service to be running.
- **The upstream `image_gen.py` is no longer executed.** Its `/v1/images/generations` and `/v1/images/edits` routes do not exist on OpenRouter; `edit` is expressed as `input_references` on the same generation endpoint. The installer still verifies `scripts/image_gen.py` is present, now purely as a download-integrity check on the npx payload.
- **Fail-closed model precheck with no escape hatch.** Every invocation calls `GET /api/v1/images/models` first and exits `4` if the target model is not listed or the list cannot be parsed, printing the first few ids that *are* available. There is deliberately no `SKIP_MODEL_CHECK`-style bypass.
- **Wider argument surface, same `--output` semantics.** `-o/--output` behaves exactly as upstream (file-vs-directory mode, `_N` suffix, never overwrites). `--size` gains the `512`/`1K`/`2K`/`4K` tiers and arbitrary `WxH`; `-i/--image` gains http(s) URLs alongside local paths; `--aspect-ratio`, `--resolution`, and `--seed` are new. `--api-key`, `--base-url`, and `--mask` are accepted but refused with an explanation, `--moderation` is accepted and ignored. Exit codes are graded `0`/`1`/`2`/`3`/`4` instead of always `1`.
- **`scripts/image-gen-cliproxyapi.sh` is removed from `~/.claude` automatically** on the next install, via a new `SUPERSEDED_USER_SCRIPTS` sweep in both installers. Without it the file would be orphaned, since the uninstall loop only knows the current `USER_SCRIPTS`.
- **Fixed: `install.ps1` looked for `image-gen\image_gen.py` instead of `image-gen\scripts\image_gen.py`** in both `Update-ImageGenSkillInstructions` and the restore-path validation. The augmentation therefore failed on every Windows run, taking the whole image-gen install down with it (as a warning, not a fatal error). Windows image-gen installation was 100% broken before this fix.
- **Fixed: the two installers emitted different SKILL.md integration blocks** (the PowerShell one carried five extra WSL lines), so alternating between them on one `~/.claude` rewrote SKILL.md every time. They are now byte-identical, and both carry a comment saying they must stay that way.
- **Removed the dead `skills/generate-image/` directory** — four orphaned `.pyc` files with no source and zero references anywhere in the repo.

### Design Rationale
- **`ANTHROPIC_API_KEY` is the empty string, in `env`, and deliberately not in `credentialKeys`.** OpenRouter authenticates with `Authorization: Bearer`, which Claude Code emits only while `ANTHROPIC_API_KEY` is falsy — any value at all flips it to `x-api-key` and the request is treated as a direct Anthropic call, so the OpenRouter token would never be sent. It lives in `env` rather than `unset[]` because `unset[]` performs a real `unset`, which is a different thing from an empty value; the empty string is what is actually specified here. The mechanism was checked rather than assumed: `_cl_profile_env_pairs` (`claude.zsh:484-498`) rejects only `array`/`object` values, and running its jq filter verbatim against `profiles/or.json` emits the line `ANTHROPIC_API_KEY=`; the injection loop (`claude.zsh:736-741`) tests for an empty *key*, not an empty value, so the export happens. Keeping it out of `credentialKeys` means the re-install merge (`install.sh:2192-2199`) rewrites the empty string from the template every upgrade, and also keeps it out of the placeholder scan — an empty string is not something the user is meant to fill in.
- **No `_SUPPORTED_CAPABILITIES` keys.** The `effort,xhigh_effort,max_effort,thinking,adaptive_thinking,interleaved_thinking` string that `glm.json` and `gpt.json` carry makes Claude Code emit Anthropic thinking/effort parameters that OpenRouter must translate into DeepSeek's `reasoning` field, and `adaptive_thinking` / `interleaved_thinking` have no DeepSeek counterpart at all — a plausible source of sporadic 400s on a path nobody has tested. Omitted, with the note telling you how to add them back one at a time.
- **`CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` is not set.** The suppression branch at `claude.zsh:555` only fires when the resolved slot variable is *empty*; all four slots are filled here, so the launcher still injects `--model opus` and the `/model` picker stays pre-locked either way. Setting it would buy no behaviour change and cost one model-list round trip at every startup. `glm.json`, the direct-connection template this profile follows, does not set it either.
- **`gpt` and `ccr` were demoted because neither is usable straight out of the installer.** `gpt` needs an external `brew` binary plus a reverse-engineered OAuth flow that carries a real account-ban risk; `ccr` keeps its config in SQLite and has to be set up by hand in a web UI. Both are backends that install fine and then do nothing — exactly the shape of dependency that 2.21.0 moved `adversarial-review` off the default path for, and the same reasoning applies here.

- **The key comes from `profiles/or.json` only — no `OPENROUTER_API_KEY` fallback.** A second credential surface for the same token would inevitably drift from the first, and the repo's existing model is that credentials live in `~/.claude/profiles/*.json` and survive upgrades via `credentialKeys`. The cost is explicit: image generation now requires the OpenRouter backend to be installed and filled in, even for users who never launch `cl_or`. The key is used only as an `Authorization` header — never in argv, a subprocess environment, stdout, stderr, or an error message — and is charset-restricted to `[A-Za-z0-9._~-]+` so it cannot inject a newline into the request headers. The unfilled `YOUR_*` placeholder is treated as absent rather than sent to the API for a 401.
- **The destination host is guarded as tightly as the key itself.** Refusing `--api-key` accomplishes nothing if the *endpoint* stays freely settable, because `Authorization: Bearer <real key>` is attached to whatever host the base URL names — so `--base-url https://evil.example/api/v1` slipped into an argument list by prompt injection would exfiltrate the token while fully honouring the `--api-key` ban. `--base-url` is therefore rejected exactly like `--api-key` (exit `2`, hidden from `--help`): argv is the surface a prompt injection controls, and nothing legitimate needs it. `IMAGE_GEN_BASE_URL` survives, because the environment is not attacker-reachable in the same way, but it is now restricted to `openrouter.ai` or a subdomain over https, plus `127.0.0.1` / `[::1]` / `localhost` over http(s) so the stub-server test path keeps working. Matching is on the parsed hostname, never a substring test — `https://openrouter.ai.evil.com` and `https://evil.com/?x=openrouter.ai` are both rejected. The check runs before the key is read, so an unauthorized host fails on its own terms rather than being masked by a missing-credential error.
- **Python, not Bash, for the wrapper.** The work is base64 encode/decode, JSON construction, and data-URL assembly; in Bash that means three or four embedded `python3 -c` heredocs (the old wrapper already had two). `python3` was already a hard requirement, and `argparse` keeps the flag semantics aligned with upstream far more reliably than hand-rolled getopt. The cost: this is the repo's first `.py` file, so `bash -n` does not cover it and `python3 -m py_compile` was added to the verification set.
- **Upstream's `.env` auto-loading was dropped deliberately.** `image_gen.py` walks up from the CWD looking for a `.env` and injects it into the environment. Generating an image while sitting in an arbitrary user repository should not read that repository's secrets.
- **Ownership validation accepts the legacy marker and manifest, but only ever writes the current ones.** This is the single most important detail in the change. Both the SKILL.md markers and the manifest's `wrapper=` line changed. Without a compatibility path, every existing install would fail `_image_gen_manifest_valid`, fail `_image_gen_dir_owned`, fall through to the "exists but is not installer-owned" branch, and be **skipped permanently** — every upgrade emitting one warning and leaving image generation frozen on the deleted CLIProxyAPI wrapper. The new `_image_gen_manifest_valid_any` / `_image_gen_markers_strict_any` validators are used at the three ownership call sites only; the write path and the post-write self-check stay strict, so the migration happens exactly once and the second run is a pure current-format idempotent pass. Augmentation strips the legacy block before inserting the current one, so a migrated SKILL.md ends up with one managed block instead of two.

### Notes & Caveats
- **The `or` backend has never been exercised against a live OpenRouter key.** The blocking curl check from the task spec was skipped by the user's decision (no key available), so whether DeepSeek `tool_use` round-trips correctly through OpenRouter's Anthropic skin is **unverified**. OpenRouter's own wording is that the native endpoint "is only guaranteed to work with the Anthropic first-party provider" — a no-guarantee, not a hard rejection, and no public report exists either way. The credential-guard *failure* path was tested (`cl_or` on an unfilled profile aborts with the placeholder error and never opens a socket); the happy path was not.
- **Existing installs are unaffected by the default change.** `install_profiles()` iterates the selected set and performs no reverse cleanup, so an already-installed `~/.claude/profiles/gpt.json` or `ccr.json` is never deleted by an upgrade, and `configure_ccr_profile` still triggers on the presence of that file.
- **`--all` is also the non-TTY `curl | bash` fallback**, and it still installs `gpt` and `ccr`. The new defaults apply to the interactive selector only.
- **No 5h quota bar on `or`.** `hooks/statusline.sh:85-90` selects a quota source from `$ANTHROPIC_BASE_URL` and only knows `bigmodel.cn` / `z.ai`; more fundamentally, OpenRouter has no 5h rolling window — only a credit balance at `/api/v1/credits`, which is money rather than a percentage of a window, and would render as a semantically wrong bar.
- **One context limit, all slots.** `CLAUDE_CODE_MAX_CONTEXT_TOKENS` is client-wide and set to `1000000` to match both DeepSeek V4 models. Repointing any slot at a 163K-context model (`deepseek/deepseek-v3.2`, `deepseek/deepseek-chat`) requires lowering it by hand. `deepseek/deepseek-reasoner` does not exist on OpenRouter — that id belongs to DeepSeek's own API.
- **`install.ps1` was not touched.** It has no profile or launcher support at all (`grep -c profile install.ps1` is 0); Windows gets the statusline only.
- **Verified**: `bash -n install.sh` under both bash 5.3 and system bash 3.2.57, and `zsh -n claude.zsh`, all exit 0; `jq empty profiles/*.json` clean; the `_cl_profile_env_pairs` filter run verbatim against `profiles/or.json` emits exactly one `ANTHROPIC_API_KEY=` line; the placeholder scan returns `ANTHROPIC_AUTH_TOKEN` only; all twelve `ANTHROPIC_DEFAULT_*` slot keys present with zero `_SUPPORTED_CAPABILITIES`. In a throwaway `HOME`: the interactive default selection installs `claude.json`, `glm.json`, `or.json` and no `gpt.json` / `ccr.json`; `--all` installs all five; `cl_or` and `cl_or_auto` are both defined after sourcing the installed `claude.zsh`; `cl_or` on an unfilled profile exits 1 with the placeholder error; the pending-setup summary lists `[or]` with the `key` + `guide` steps only (no install/login, since `service` is `null`); and a re-install over a hand-edited profile preserves `ANTHROPIC_AUTH_TOKEN` while resetting `ANTHROPIC_API_KEY` to `""` and non-credential keys to the template values.

- **BREAKING for existing users: image generation stops working until you configure OpenRouter.** Migration: re-run the installer, tick **OpenRouter** in the Model Backends group, then put a key from <https://openrouter.ai/keys> into `~/.claude/profiles/or.json` as `.env.ANTHROPIC_AUTH_TOKEN`. Until that key is filled in, the wrapper exits `3` with an explanatory message. The old `~/.claude/scripts/image-gen-cliproxyapi.sh` is deleted automatically by the same install; nothing needs to be cleaned up by hand. Existing `~/.claude/skills/image-gen/` installs are migrated in place, not skipped (see the ownership note above).
- **The OpenRouter image path has never been exercised against a live key.** No end-to-end generation, no image-to-image round trip, and no confirmation of the request/response shapes against the real API. The `input_references` object shape comes from OpenRouter's published documentation, not from an observed request.
- **The biggest single unverified risk: whether `openai/gpt-image-2` actually appears in `GET /api/v1/images/models`.** That endpoint requires authentication, so it could not be queried. What was confirmed earlier is that the id appears in `GET /api/v1/models?output_modalities=image` — a *different* endpoint whose list is not guaranteed to be identical. If the two disagree, the fail-closed precheck will block every request. The failure is loud and self-correcting rather than silent (the error lists the first few genuinely available ids, and `--model` overrides), but it is the first thing to test once a key exists.
- **Whether `size` / `quality` / `background` / `output_compression` are supported by `openai/gpt-image-2` specifically is unverified.** `GET /api/v1/images/models/{id}/endpoints` reports per-model `supported_parameters` but needs auth. Unsupported parameters are expected to come back as a 4xx, which the wrapper surfaces verbatim.
- **`install.ps1` was changed but not executed.** No `pwsh` is available in this environment, so even the syntax check was skipped — the PowerShell changes (legacy-block byte-splice, the `*Any` validators, the two path fixes, the superseded-script sweep) rest on review against the Bash implementation alone. The byte-level legacy strip in `Update-ImageGenSkillInstructions` is the riskiest of these and needs a real Windows run.
- **The two legacy-strip implementations now agree on malformed input.** Both remove the interval only when the file holds exactly one legacy BEGIN, exactly one legacy END, and BEGIN precedes END; every other shape (none, duplicated, one-sided, end-before-begin) is an identity transform that leaves the text for the current-marker validation to judge. The Bash side previously used a stateless `awk` skip-toggle, which meant a single unmatched legacy BEGIN — from a hand-edited SKILL.md, an interrupted install, or a line that merely equalled the old marker text — latched `skip` on and **discarded every remaining line of the file**, including the intact current marker block below it. The truncated file then failed the strict check, silently degraded to append mode, and was written back over SKILL.md with no warning and a zero exit code. Reproduced before the fix (an 8-line fixture came out as 1 line) and confirmed fixed across all seven shapes.
- **Verified in this change**: `bash -n install.sh` under bash 5.3 and system bash 3.2.57; `python3 -m py_compile` and all three `--help` forms on the new wrapper; `jq empty profiles/*.json`; `scripts/check-readme-sync.sh`; and the two SKILL.md integration blocks confirmed byte-identical by `cmp`. Against a local stub HTTP server: a real PNG is decoded and written, the path is printed to stdout, `revised_prompt` goes to stderr, the key appears only in the `Authorization` header, nested output directories are created, an existing target is never overwritten (`pic.png` → `pic_2.png`), and `edit` sends a correctly-shaped base64 data-URL `input_references` entry. With the target model absent from the stub's model list the run exits `4` having sent **zero** POST requests, confirming fail-closed. A 25-assertion harness over the real `install.sh` functions covers idempotency (two augment runs byte-identical, exactly one marker pair) and the full legacy upgrade: a CLIProxyAPI-era manifest and marker block are recognized as owned, the legacy block is stripped, exactly one current block replaces it with surrounding prose preserved, the manifest is rewritten to canonical, and the following run is byte-identical. In a throwaway `CLAUDE_DIR`, `install_scripts` installs the new wrapper executable and removes the superseded one, while `--dry-run` reports both actions without touching disk. ## [2.20.0] - 2026-08-14

### Features
- **The statusline's 5h quota bar now follows whichever backend the terminal is actually on.** It previously only ever knew one endpoint — `api.anthropic.com/api/oauth/usage` with the OAuth token out of the keychain — so a terminal running `cl_glm_auto` either showed the wrong account's numbers or nothing at all. The backend is now derived from `$ANTHROPIC_BASE_URL`: empty means native Anthropic and takes the existing path unchanged; `bigmodel.cn` or `z.ai` means the GLM Coding Plan; anything else (the `127.0.0.1:8317` gpt proxy, the `127.0.0.1:3456` ccr gateway) has no quota endpoint we can speak to and renders no quota segment at all.
- **GLM quota comes from `{scheme}://{host}/api/monitor/usage/quota/limit`**, the endpoint Zhipu's own `glm-plan-usage` plugin uses. The host is taken from `$ANTHROPIC_BASE_URL` rather than hardcoded, because the mainland deployment is `open.bigmodel.cn` and the international one is `api.z.ai`. Authorization is the raw `$ANTHROPIC_AUTH_TOKEN` — this endpoint 401s on a `Bearer ` prefix.
- **Non-native quota segments are labelled.** GLM renders as `glm 5h`; a bare `5h` still means the native Anthropic quota. Both reuse the existing `build_bar()` gradient and both still vanish entirely when there is no usable data.
- **Cache and lock filenames now carry a per-backend fingerprint** (`claude-usage-cache-anthropic.json`, `claude-usage-cache-glm-<checksum>.json`), replacing the single global `claude-usage-cache.json`.
- **`CL_NO_USAGE` turns the whole thing off.** `export CL_NO_USAGE=1` in `~/.zshrc` forces the backend to `other`, so no quota is fetched on any backend and no quota segment is rendered. It has to be exported, not written as a one-shot `CL_NO_USAGE=1 cl_glm` prefix — unlike `CL_MODEL`, nothing in the launcher re-exports it for the statusline's process. Named after the existing `CL_NO_FABLE_WARN`.
- **Credentials are passed to `curl` on stdin, never in argv.** Both fetch paths write their headers into a `curl -K -` config instead of `-H "Authorization: …"`, so the OAuth token and the GLM plan key no longer appear in `ps` output for every other user on the machine. Verified by sampling `ps -Ao args` throughout a live fetch: the `curl` command line carries only `-K -` and the URL, while the header still arrives at the server byte-exact (checked against a local listener with a token containing `"` and `\`, the two characters curl's config format escapes).

### Design Rationale
- **GLM polls on a 600s TTL, not the 60s the native API gets.** Zhipu's usage terms state that the platform applies rate limiting and that accounts violating its rules can be throttled or frozen, and they explicitly do not publish the full enforcement logic. The statusline fires on *every* render, which for an active session is far more often than once a minute, so an undocumented threshold is a real risk on an endpoint that is not part of the advertised API surface. 600s is also where the two known community implementations landed independently (`cc-zaiquota` defaults to 600s, Darkycl's to 5 minutes). The native path keeps its 60s TTL because it is a first-party endpoint the client itself already polls.
- **The negative-cache backoff is per backend and never shorter than that backend's TTL** — 600s for GLM, 300s for native. A single hardcoded 300s would have made GLM poll a *failing* endpoint twice as often as a healthy one, which is exactly backwards for the backend whose risk controls are the reason for the long TTL in the first place. The two backends' constants now live in one `case` rather than an `if`/`else`, because the old `else` arm silently served both `anthropic` and `other` and would have mis-served any third backend.
- **The 5h window is identified by an upper bound on its reset time, and only when that identification is unambiguous.** The response returns several `TOKENS_LIMIT` entries and encodes the window size in a `unit` field whose meaning is not documented and which different community clients read differently — some key on `unit == 3`, some on a `number == 5`. Any of those is one upstream field rename away from silently showing the multi-day quota as if it were the 5h one, so no size field is read at all. What is used instead is a bound that holds by construction: the 5h window's `nextResetTime` is always within 5h of now (6h is applied, for clock skew). **This is a heuristic, not a definition, and it does not on its own identify the window** — a weekly window inside the last minutes before its own reset also satisfies the bound. Picking the soonest-resetting survivor, the obvious next step, is therefore wrong: for roughly 6 hours in every 168 it would relabel the weekly quota as `glm 5h` and display a confidently incorrect number. So the window is taken only when exactly one candidate survives the bound; when two or more do, the segment renders nothing. A missing bar is recoverable by looking anywhere else, a wrong percentage is not.
- **The reset time is taken verbatim from `nextResetTime` and never computed from a clock boundary**: GLM's window is rolling — it restarts five hours after the request that opened it, so any locally derived "next top of the 5h block" would simply be wrong.
- **Every number that reaches the bar is type-checked twice.** The `jq` normaliser requires `percentage` and `nextResetTime` to actually be JSON numbers, and the renderer re-validates the cached value as a plain decimal before any arithmetic. Checking once was not enough: `printf "%.0f" "N/A"` emits a partial `0` *before* it fails, so the old `printf … || echo "$raw"` produced the string `0N/A`, which then reached `$(( pct * w / 100 ))` and put a bash `value too great for base` error on stderr — a visible crash in a component whose whole contract is to degrade silently.
- **The stale-lock reclaim is itself locked.** `stat` → compare → `rm -rf` → `mkdir` is a TOCTOU window: several renders can each judge the same lock stale, and a late `rm -rf` deletes the lock a peer has just created, leaving two "holders" that both hit the upstream API — precisely the concurrent traffic the long TTL exists to avoid. Reclaiming now requires first winning a second `mkdir` lock, after which the stale check is repeated. That reclaim lock is itself subject to the same 120s staleness rule, so a process killed mid-reclaim cannot become a new permanent wedge.
- **Caches are split by fingerprint because the user runs both backends concurrently on one machine.** With a single global cache file, two terminals would alternately overwrite each other and each would display the other's numbers half the time. The fingerprint is the backend name plus a `cksum` of the credential, so switching GLM accounts — or running the mainland and international keys side by side — also gets separate files. `cksum` rather than `shasum`/`md5` because it is POSIX and present under Git Bash, where the others are not guaranteed. The token is hashed, never written into the filename.
- **The refresh lock is a `mkdir`, not a lockfile.** `mkdir` fails atomically when the directory exists, which the old `[ -f ]`-then-`echo $$ >` sequence did not — under the concurrency this release is specifically built for, several terminals could each decide the lock was free and all fetch. Locks older than 120s are reclaimed so a killed terminal cannot wedge refreshes permanently. Cache writes go to a same-directory temp file and are renamed into place, so a reader can never see half a JSON document.

### Notes & Caveats
- **No live request was made to Zhipu during development or testing.** Every test drove the renderer from fixture cache files built by running the real response sample through the exact `jq` filter the script uses; the one path that did invoke `curl` pointed at a deliberately unresolvable host to exercise the failure branch. The endpoint URL, auth header shape, and response schema are taken from Zhipu's `zai-org/zai-coding-plugins` and from a prior confirmation that the endpoint exists — **the parsing has not been validated against a live response**, and a schema difference between the sample and what a given account actually returns would show up as a missing quota segment rather than an error.
- **One schema difference would NOT show up as a missing segment, and it is the hardest failure here to notice.** If `percentage` turns out to be a 0–1 fraction rather than 0–100, every check in the pipeline passes — it is a number, it is finite, the arithmetic succeeds — and the bar renders normally while permanently reading `0%`. A quota bar that is always empty looks like an unused quota, not like a bug. **To close it: compare one live render against the figure on Zhipu's own usage page.**
- **The native Anthropic path renders identically given identical cache content**, confirmed by feeding the same `five_hour` JSON to the pre-change and post-change scripts and diffing the output. What is *not* unchanged is the cache filename: `claude-usage-cache.json` became `claude-usage-cache-anthropic.json`. An existing user's first render after upgrading therefore finds no cache and shows no quota segment; the background refresh lands within a few seconds and the next render is normal. The old `claude-usage-cache.json` and `claude-usage-fetch.lock.d` are not migrated or deleted and will sit in `$TMPDIR` until the OS clears it. This is the same one-render gap the GLM side has, and it was previously documented only for GLM.
- **Verified**: `bash -n` on `hooks/statusline.sh` and `install.sh` under both bash 5.3 and system bash 3.2.57. Lock mutual exclusion holds under concurrent contention over a single stale lock, including the interleaving that made the pre-fix reclaim path hand out several simultaneous holders; a fresh lock blocks everyone and a dead reclaim lock resolves on the next attempt rather than wedging. Cache writes are atomic under concurrent readers and writers. Three identities (native, `open.bigmodel.cn` key A, `api.z.ai` key B) render side by side from separate caches with no cross-contamination. All failure paths — `other` backend, GLM base URL with no token, unreachable host, non-numeric / null / absent `percentage`, corrupt cache file — produce exit code 0, an empty stderr, and a statusline missing only the quota segment.
- **A GLM terminal whose cache is older than 30 minutes shows no quota segment** until the next background refresh lands, one render later. That is the intended trade-off of the long TTL, not a bug, but it does mean the first render after opening a terminal is usually quota-less.
- **`ANTHROPIC_API_KEY` is accepted as a fallback when `ANTHROPIC_AUTH_TOKEN` is unset**, but `profiles/glm.json` sets the latter, so this is defensive only.
- **Backend detection matches on substrings of `$ANTHROPIC_BASE_URL`.** A future non-GLM endpoint containing `z.ai` would be misclassified. Detection is env-based and therefore only as reliable as the launcher's exports — `profiles/claude.json` explicitly unsets `ANTHROPIC_BASE_URL`, and no `ANTHROPIC_*` variables are exported from the user's shell profile, so an empty value genuinely means native.

## [2.18.3] - 2026-08-09

### Fixed
- **On any machine with coreutils installed, every `claude plugin` call froze instead of running, and the installer burned its full timeout budget making zero progress.** GNU `timeout(1)` in its default mode calls `setpgid(2)` before forking, so the wrapped command lands in a process group that is not the terminal's foreground group. `claude` is an Ink/React TUI: it calls `tcsetattr(3)` on the tty during startup to set up raw mode, and `tcsetattr` from a background process group raises `SIGTTOU`, whose default action *stops* the process. Measured: `Adding marketplace…` prints (writes from a background group are allowed while `TOSTOP` is off), then the process sits in state `T` within ~2.5s — before any network work — and `timeout` only reaps it at expiry. `SIGCONT` alone re-stops it in a loop. Both coreutils branches now pass `--foreground`, which suppresses the `setpgid` and leaves the command in the terminal's foreground group. Same command with the child left in the foreground group: 20–31s to success.
- **`--kill-after=5` added alongside it.** `--foreground` makes `timeout` signal only the direct child rather than a process group, giving up the escalation it would otherwise do. The explicit `--kill-after` restores the TERM-then-KILL grace that the perl branch already implements by hand, so a command that ignores `TERM` still dies. The value matches the perl branch's 5s poll and the bash watchdog's `sleep 5`, so all four backends give a stubborn child the same grace rather than disagreeing on an arbitrary constant. Verified: a `trap "" TERM` sleeper under a 2s cap exits at 7s (2 + 5) on every branch, not at the cap and not never.
- **`timeout(1)` exits 137 when its own `KILL` is what reaped the child**, which would have broken the helper's "124 on timeout" contract that the perl and bash-watchdog branches uphold. Both coreutils branches now map 137 to 124.

### Changed
- **`timeout_backend()` reports `timeout(1) --foreground` / `gtimeout(1) --foreground`.** The label exists so a stall reported from someone else's machine is diagnosable from the log alone; with the flag in it, a fixed build and an unfixed one are distinguishable at a glance in the next bug report.
- **The marketplace-add, plugin-install, and marketplace-refresh loops each name the item before starting it.** Previously the loops printed only a single header and then whatever the CLI chose to emit, so a legitimately slow clone and a hung one looked identical. Naming the in-flight item is what made the freeze above diagnosable in the first place. The plugin *update* loop is left alone — it already prints a per-plugin `ok`/`warn` and adding a third line per plugin would only add noise.

### Design Rationale
- **Only the coreutils branches were affected, which is why this reproduced on some machines and not others.** The perl branch forks and waits without ever touching process groups; the bash watchdog backgrounds the command with `&`, which in a non-interactive shell (no job control) also leaves it in the caller's group. Only `timeout(1)` relocates the child. The reporting user's log said `via timeout(1)`; a stock Mac, which ships neither coreutils binary, takes the perl branch and never saw this.
- **The CLI's own 120s internal cap could not save it.** `NET_TIMEOUT` was deliberately set above that cap in 2.18.2 so the CLI would hit its own limit first and clean up after itself. That ordering assumes the CLI is *running*. Stopped before it starts its clone, it never reaches its own timer, so the 180s × 2 attempts + 3s backoff — 363s per marketplace — elapsed with nothing happening.

### Notes & Caveats
- **`--foreground` means `timeout` signals only the direct child, not a tree.** A `git` process forked by `claude` can survive the kill and keep writing the marketplace directory. This is the same grandchild gap the perl and bash-watchdog branches have always had (see 2.18.2), so the fix does not make the situation worse — it makes the coreutils branch behave like the other two. Signalling the whole group is precisely what causes the freeze, so it is not an available trade.
- **busybox `timeout` was never affected, and is now explicitly routed around.** It does not `setpgid`, so it never had the freeze — but it also rejects `--foreground` outright, and `command -v timeout` cannot tell a busybox applet from a GNU binary. Each of `timeout` and `gtimeout` is therefore probed once per run with the exact flag set that will be used (`--foreground --kill-after=5 1 true`), the verdict cached in a plain scalar (bash 3.2 has no associative arrays), and a binary that fails the probe is skipped entirely so the next backend — perl on Alpine and most minimal images — takes over. The two names are probed independently, because a machine can carry a busybox `timeout` and a GNU `gtimeout` at once. Falling back to a flag-less `timeout(1)` was rejected: on a GNU system that is precisely the freeze this release exists to fix. `timeout_backend()` runs the same probe, so the logged label names the branch actually taken.
- **Unverified by automated tests** (`tests/` was removed in `68f30f8`). Verification was manual under system bash 3.2.57 against a real GNU coreutils 9.11 `timeout`, exercising all four branches by manipulating `PATH`: exit-status passthrough (0, 1, 7), 124 at the right wall clock on timeout, 124 after the 5s escalation for a `TERM`-ignoring child, literal argument passing (`'a b'`, `'c;d'`), stderr passthrough, stdin at EOF. The busybox path was covered with a stub `timeout` that rejects `--foreground` the way the applet does: the probe fails, the perl branch is selected, the label reads `perl`, and every behavioural check still passes. A stub `timeout` paired with the real `gtimeout` selects `gtimeout`, confirming the probes are independent. The probe fires once per shell — twice per run, since `timeout_backend()` is called inside a command substitution whose cache cannot propagate back — and not once per `with_timeout` call. The `setpgid` mechanism was confirmed directly — under plain `timeout` the child's pgid differs from the shell's, under `--foreground` it matches. The SIGTTOU stop itself was not re-reproduced here (no controlling tty in the verification environment); that evidence comes from the original diagnosis. `--dry-run --all` completes and prints the new backend label; the new per-item progress lines do not appear under `--dry-run`, which has its own `Would add`/`Would install` messages.

## [2.18.2] - 2026-08-09

### Fixed
- **The bash timeout watchdog held the caller's output pipe open for the full timeout after the command had already succeeded.** `with_timeout`'s fallback forked `( sleep "$secs"; kill ... ) &`, a subshell inheriting the installer's stdout and stderr. When the wrapped command finished early, `kill -TERM "$watchdog_pid"` killed only the subshell — the `sleep` it had already forked was reparented to init and ran to completion, still holding the inherited pipe's write end. Any reader waiting for EOF (`| tee`, `$(...)`, a CI log capture, an agent's shell tool) therefore stalled for exactly `NET_TIMEOUT` seconds per call, regardless of how fast the command returned. Measured on a fast-returning command: 20s stall under the old code, 0s under the new. On a bare tty there is no EOF-waiting reader, which is why this never reproduced interactively.
- **A perl branch now sits between `gtimeout(1)` and the bash watchdog.** macOS ships neither coreutils binary but always ships perl, whose `alarm` puts the timer inside the waiting process — there is nothing left over to orphan. It forks, waits, and exits with the child's real status, or 124 on timeout after a TERM-then-KILL escalation that polls for exit instead of sleeping a flat 5s. The bash watchdog remains as a last resort and now sends its own output to `/dev/null`, so even there an orphaned `sleep` cannot hold the caller's pipe.
- **A command finishing on the same instruction boundary the alarm fires on is no longer misreported as a timeout.** The main `waitpid` can reap the child before perl dispatches the pending `SIGALRM`; the handler's `waitpid` then returns -1 (ECHILD) and the old loop, testing only `> 0`, would spin its full 5s grace and `exit 124` over a command that had succeeded. The handler now saves `$?` on entry and returns the real status when the child is already gone.

### Changed
- **`NET_TIMEOUT` 60s → 180s, and marketplace/plugin attempts 3 → 2.** The `claude` CLI caps its own clone and cache refresh at 120s; the previous 60s sat *below* that, so this script fired first and killed the CLI without reaching the `git` it had forked — leaving an orphan writing the marketplace directory while `retry` started the next attempt against the same path. The cap is now a backstop above the CLI's own limit, letting the CLI hit its bound first and clean up after itself. Dropping to 2 attempts keeps the worst case bounded despite the 3× cap: 363s per marketplace, ~243s in practice.
- **The `Adding marketplaces` line now names the active timeout backend** (`timeout(1)`, `gtimeout(1)`, `perl`, or `bash watchdog`). A stall reported from someone else's machine is diagnosable from the log alone — the four branches have materially different failure modes.

### Design Rationale
- **perl forks and waits rather than `alarm` + `exec`.** `alarm(2)` does survive `exec(2)`, making the one-liner `perl -e 'alarm shift; exec @ARGV'` tempting. But `exec` resets signal handlers, so `SIGALRM` kills the process by default action and bash prints `Alarm clock: 14` to stderr on every timeout. Forking costs one extra process and buys a clean `exit 124` plus the TERM-before-KILL grace the old watchdog had.
- **Indirect-object `exec {$ARGV[0]} @ARGV` never routes through a shell**, so command words containing spaces or metacharacters stay literal. Verified with `printf '[%s]\n' 'a b' 'c;d'`.

### Notes & Caveats
- **The 120s figure is an assumption about the `claude` CLI recorded only in a comment.** Nothing validates it at runtime. If a future CLI raises its internal cap above 180s, the orphan-`git` race returns.
- **Killing still does not reach grandchildren.** Neither branch puts the command in its own process group, so a `git` forked by `claude` can outlive the kill. Process-group signalling would fix it but would also detach the command from the terminal, so a `Ctrl-C` on the installer would stop reaching it. The `NET_TIMEOUT` > CLI-internal-timeout ordering is the mitigation instead.
- **Unverified by automated tests** (`tests/` was removed in `68f30f8`). Verification was manual under system bash 3.2.57: exit-code passthrough (0/1/7), 124 on timeout, 8s total for a TERM-ignoring process under a 3s cap (3 + 5s grace), stderr passthrough, stdin at EOF, literal argument passing, a 30-iteration run against the alarm boundary confirming no 5s spin, an end-to-end `claude plugin marketplace update` through a pipe (1s, was 180s worst case), and `--dry-run --all`.

### Fixed

- **`with_timeout <seconds> <command...>` wall-clock guard on all network operations.** Applied to `claude plugin marketplace add`, `claude plugin marketplace update`, `claude plugin install`, and `claude plugin update`. Prefers coreutils `timeout(1)`/`gtimeout(1)` and falls back to a bash watchdog (`TERM`, then `KILL` after 5s), because macOS ships neither — on a stock Mac the fallback is the live path, not a corner case. - **`GIT_HTTP_LOW_SPEED_LIMIT` / `GIT_HTTP_LOW_SPEED_TIME` exported (1024 B/s over 30s).** Aborts a transfer that stalls on a half-dead connection instead of burning the full `NET_TIMEOUT` on a socket moving no bytes. Retries on the refresh drop from 3 to 2, since the per-catalog cap now bounds each attempt.

- **Naming each marketplace is what buys the isolation.** `claude plugin marketplace update` accepts an optional `[name]`; without it the CLI decides the order and the installer cannot tell which remote is stalling. - **`temp_<epoch>` directories are skipped by name.** They are the CLI's in-flight scratch clones, not catalogs; they appear and vanish during any concurrent update (including the CLI's own background refresh) and are already swept by `scripts/cleanup-claude-data.sh`.
- **A bash watchdog rather than requiring coreutils.** Adding a `brew install coreutils` prerequisite to a `curl | bash` installer in order to fix a hang is a worse trade than ~15 lines of `kill`-on-timer, especially when macOS is the primary target.
- **`--depth 1` was investigated and rejected as a no-op.** Every marketplace clone under `~/.claude/plugins/marketplaces/` is already shallow at exactly 1 commit — the CLI clones that way. The 86 MB of `ecc` is working-tree content, not history, so there is no depth left to trim.

- **This is unverified by automated tests**, as the `tests/` harness was removed in `68f30f8`. The installer never invents a value: it resolves the URL by strict precedence — **existing valid config `proxy-url` > explicit `GPT_PROXY_URL` env var > omitted** — before any filesystem write, and the normalized config optionally carries a 6th line (`proxy-url: "…"`) between `auth-dir` and `api-keys`. Accepted schemes are `http://`, `https://`, `socks5://`, `socks5h://`; credentials in the URL (`scheme://user:pass@host:port`) are allowed. `docs/BACKENDS.md` and `docs/BACKENDS.zh-CN.md` document the contract end-to-end.
- **Standard proxy env vars are deliberately not auto-persisted.** `HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY` are ignored by the resolver — they routinely carry short-lived credentials, and silently writing them into `config.yaml` would break idempotency and leak secrets at rest. Use the explicit `GPT_PROXY_URL` (or a hand-written `proxy-url:`) to opt in.
- **Fail-safe on a malformed `proxy-url`.** A top-level `proxy-url:` that is present but unparseable, has an unsupported scheme, or contains control/YAML-injection characters causes `configure_gpt_backend` to increment `INSTALL_CRITICAL` and return **without touching** `config.yaml` or `gpt.json` (no silent rewrite that strips the user's value). A malformed explicit `GPT_PROXY_URL` fails the same way.

### Design Rationale
- **Precedence mirrors the key.** The key resolver already treats the existing config as authoritative and falls back to a single explicit env var; the proxy resolver follows the same shape (`config > GPT_PROXY_URL > none`) so users reason about one ladder, not two. The URL value is captured through a temp-file redirect (never command substitution) so `GPT_PROXY_SOURCE` lands in the calling shell and the value is never echoed, logged, or leaked — not even under `set -x`, which the coordinator suppresses for the inner function. The renderer defensively double-quotes the scalar and rejects values containing `"`, `\`, or whitespace/CR/LF/tab, so a malicious `proxy-url` cannot rewrite the normalized document.
- **One outbound proxy, two independent planes.** CLIProxyAPI's `proxy-url` (port `8317`, the `gpt` backend) and CCR's upstream proxy (port `3456`, the `ccr` backend) are intentionally separate and never share state. CCR runs on its own port `3456`, loads its upstream proxy via the `gateway-proxy-preload.cjs` preload + the `CCR_UPSTREAM_PROXY_URL` env var backed by Undici's `ProxyAgent`, and exposes no enabled proxy setting in its GUI; `cl_ccr` therefore never traverses CLIProxyAPI on `8317`. Documenting both in the same subsection keeps the boundary explicit.
- **Why a 6th line and not a separate file.** CLIProxyAPI reads `proxy-url` from the same `config.yaml` it already loads via `--config`, so reusing that file (rather than introducing a sidecar) keeps a single source of truth, matches the launcher's hard-coded path, and lets the existing idempotency/backup machinery apply unchanged: a config already normalized with `proxy-url` is a byte-for-byte no-op on re-run (no backup written).

### Notes & Caveats
- **A direct-connect first run can enter an auth-cooldown.** With no `proxy-url`, CLIProxyAPI connects to OpenAI directly; an initial 500 from the upstream can trigger a secondary `503` auth-cooldown state that persists for the process. Routing the upstream through a stable `proxy-url` avoids the direct-connect path. This is upstream CLIProxyAPI runtime behaviour, not installer behaviour.
- **The proxy URL is treated as a secret.** It may contain credentials and is never printed by the installer, the resolver, or the renderer; captured output and xtrace are both scrubbed. Store it in `~/.cli-proxy-api/config.yaml` (mode `600`) or pass it via `GPT_PROXY_URL` for a single run.
- **Windows unchanged.** `install.ps1` still does not create or write `~/.cli-proxy-api/config.yaml`; `proxy-url` reconciliation is Bash/Zsh-only, identical to the rest of GPT auto-configuration.

- **`CLAUDE_CODE_MAX_CONTEXT_TOKENS` is the intended escape hatch, and the only one.** Claude Code's context resolver returns a hardcoded 200000 for any model id that is not `claude-*`, does not match `/\[1m\]/i`, and is not in its built-in registry — which is every `glm-*` id. The env var is honoured precisely because the id is not `claude-*`. The `[1m]` suffix route was rejected: `glm-5.2[1m]` is not a Z.ai model code and would be sent on the wire.

- **Output is `128000`, not `131072`.** Z.ai documents 128K max output for glm-5.2, but the client clamps `CLAUDE_CODE_MAX_OUTPUT_TOKENS` to at most 128000, so the literal 131072 would be silently reduced. 128000 is the largest value that survives.
- **One profile with a documented caveat, not two profiles.** See below — a second `glm-200k` profile would double the surface (installer entry, baseline, migration, docs) to guard a limit that only bites past 200K on a non-default slot.
- **`--model` is parsed, not positional.** `claude` accepts a bare prompt as its first positional argument, so consuming `cl_glm <name>` as a model would break `cl_glm "write a haiku"`. Honouring claude's own flag costs the user nothing new to learn, and `CL_MODEL` covers the "change my default" case.

### Notes & Caveats
- **One context limit, three models.** `CLAUDE_CODE_MAX_CONTEXT_TOKENS` is client-wide, not per-slot. It is set to glm-5.2's 1M because glm-5.2 is the opus slot *and* the launcher default. - **No new slot for `glm-5v-turbo`.** Claude Code exposes exactly three model slots (haiku/sonnet/opus) and all three are taken by Coding Plan models. The vision model is reachable through `--model glm-5v-turbo` instead of displacing one.
- **Existing installs pick the new env keys up automatically.** `install_profiles` takes the template wholesale and re-applies only `credentialKeys`, so the three new variables arrive on the next run with the API key preserved. A hand-edited `glm.json` is backed up and the reset fields are listed, as before.

## [2.7.0] - 2026-06-08

### Features
- **Fork-friendly installers: repository metadata is now configurable** (#41, thanks @Yastruhank). `install.sh` and `install.ps1` no longer hard-code `Mizoreww/awesome-claude-code-config/main`. The owner, name, and branch are read from `REPO_OWNER` / `REPO_NAME` / `REPO_BRANCH` (defaulting to the upstream values) and composed into every download URL — tarball/zip source, the remote `VERSION` check, and the `Show-Help` remote-install one-liner. This lets a fork or mirror run the installer (including the `curl | bash` / `irm | iex` remote forms) without editing source.

### Bug Fixes
- **Validate repository-metadata overrides to prevent command injection.** In remote mode `install.sh` builds the download command from `REPO_URL` and executes it via `bash -c`. The new env-controlled `REPO_OWNER`/`REPO_NAME`/`REPO_BRANCH` are now validated against a safe charset (`^[A-Za-z0-9._-]+$`, plus `/` for branch refs) before use, mirroring the existing `VERSION` guard. The remote `version` sanitizer also now permits `/` so `feature/*` branches work as a `REPO_BRANCH` override.
- **Remove invalid `mcp__*` wildcard from `permissions.allow`**: Claude Code's `/doctor` rejects a bare `mcp__*` in *allow* rules. In allow rules a glob is only valid in the **tool position** after a literal `mcp__<server>__` prefix (e.g. `mcp__github__*`) — the server-name segment itself cannot be globbed. The entry was silently skipped, so removing it is behaviour-preserving (MCP tools already fell through to the `auto` permission prompt). To pre-allow MCP tools, add valid per-server entries such as `mcp__github` or `mcp__github__*`. (Deny/ask rules still accept wildcards anywhere.)

### Design Rationale
- **One override per field, not two.** The contributed PR shipped both `REPO_OWNER` and a parallel `REPO_OWNER_OVERRIDE` (×3 fields, ×2 scripts) with a hidden precedence rule. These were collapsed to a single variable per field — same capability, no ambiguity about which one wins.
- **Validate at the boundary.** The override values cross a trust boundary (environment → shell-evaluated URL), so they are checked the moment they are read, consistent with the project's existing input-validation stance.

### Notes & Caveats
- The PR's experimental `--dry-run` directory guard was reverted: it only covered the top-level `$CLAUDE_DIR` `mkdir`, while component installers still create subdirectories (and remove legacy skills) before their dry-run checks — so it gave a false sense of safety. Making `--dry-run` fully non-mutating is tracked as a separate follow-up.
- Comment-based help blocks in both scripts still reference the upstream URL literally; PowerShell's `<# … #>` help is static text parsed by `Get-Help` and cannot interpolate runtime variables.

## [2.3.0] - 2026-04-10

### Features
- **Adaptive statusline wrapping**: Statusline now dynamically wraps segments to the next line based on terminal width instead of being truncated. Uses visible-width calculation with ANSI-aware measurement.
- **Adaptive progress bar sizing**: Context and 5h usage progress bars shrink (min 8 chars) when terminal space is tight, staying on the same line when possible.

- **Negative bar sizing clamp**: When preceding segments exceed available space, adaptive bar sizing now correctly clamps instead of silently using full 20-char width.

### Design Rationale
- Segment array architecture replaces string concatenation for clean separation of layout concerns
- PPID fd walk is more correct than `/dev/pts/*` glob which could read another session's terminal

### Notes & Caveats
- Wrapping only occurs at segment boundaries; a single segment wider than terminal will overflow naturally
- Hardcoded label overhead estimates (18/14 chars) may drift by 1-2 chars on edge cases
